## NPU 軌道：今天的完整結論

### 已證明可用

| Probe | 結果 |
|---|---|
| `toy_conv`（Conv+Relu，2 節點） | PASS 1/1，整圖上 NeuronEP + apusys session |
| `ConvStackPlusUnsupported`（9 節點，含 Softmax） | PASS 1/1 |
| `BigConvStack`（240 節點） | PASS 1/1 |
| **TFLite + Neuron Stable Delegate（mobilenet_v2 float）** | **CPU 34.6ms → NPU 2.68ms，12.9×** |

### 已否證（附證據）

- **ORT-NeuronEP 路徑**：SenseVoice FP32 與 int8 兩版皆在 session 初始化崩潰
  `unordered_map::at`。六個假設全部實測排除（量化格式、12 個算子、int64 輸入、
  4 輸入簽章、CPU fallback、圖規模），**原因未定位**。MediaTek 官方自承此 EP
  「in active development」。詳見 `edge/npu_spike/ADR-npu-path.md` §8。
- **我先前重開停損時給的理由是錯的**：主張 int8 的 dynamic-quant 算子是主因，
  但 FP32 版零量化算子、同一錯誤。已記錄於 ADR §8.2。
- **「NeuronEP 全收或全不收」的推論也是錯的**，已於 `REOPEN-OP-TRIAGE.md` 更正。

### 今天的突破

`mtk_converter` 8.13.0（NP8 public 層）**16.8 秒**轉出 SenseVoice TFLite，
而 onnx2tf 兩條 backend 都失敗。流程已寫成 `edge/np8/convert_sensevoice_tflite.py`。

三個缺一不可的前處理（都是撞到才發現）：
1. 釘住 `x_length=200`，**dtype 必須 INT32**（INT64 會讓下游 `Add` 綁兩種型別）
2. 常數摺疊必須用 `ORT_ENABLE_BASIC`（`EXTENDED` 會引入 `com.microsoft` 融合算子）
3. 清掉未使用的 opset 宣告（檢查看宣告不看實際使用）

摺疊效果：節點 9082 → 3807，`Range` 3 → 0。

### 未解與限制（不得粉飾）

- **937MB float 版放不進裝置**（3.7GB 總量，Phase 8 峰值 2723MB）。實際部署需量化版，
  而量化需要真實 fbank 校準資料，**尚未進行**。
- ORT 折疊時警告 `logits` 宣告 shape `{1,200,25055}` vs 實際 `{1,204,25055}`。
  **是否影響輸出正確性未驗證。**
- MDLA 明確拒收 `BatchMatMul`（有 target report 佐證），SenseVoice 有 421 個 MatMul，
  **即使轉檔成功，加速幅度仍存疑**。PreOpCheck 就是要回答這個。

## GPU：唯一還沒被否證、且不需 NDA 的加速路徑

`server/config.py:144` 註解寫「Genio 520 弱腦、**無 GPU**」——**這是錯的**：

```
/dev/mali0  → Mali-G57 2 cores
vulkaninfo  → deviceName = Mali-G57, apiVersion 1.3.274
clinfo      → ARM Platform, OpenCL 3.0, cl_khr_fp16
```

llama.cpp 有成熟的 Vulkan backend、吃現有 GGUF 不需轉檔，直接打 71% 的瓶頸。
但板上 binary 沒編進 GPU 後端（`--list-devices` 為空），需重編。
風險：Mali-G57 僅 2 核、與 CPU 共用記憶體，實測可能不比 6 執行緒 CPU 快。

### 結論一：硬體加速的邊際報酬是零

加分條件是「採用國產晶片平台實現**近端原型演示**」——**Phase 8 已達成**（真機跑完整
離線迴圈）。那 2 分**已經到手**。NPU/GPU 加速**不會再多給任何分數**。

2026-07-27 一整天投在 NPU 上的成果（排除 ORT 路徑、mtk_converter 轉檔成功、確認
GAI Toolkit 是 NDA 門檻）有其價值，但**接下來不應再往硬體加碼**，除非明天工作坊
帶回能低成本落地的答案。

### 結論二：主軸應放在「普惠」

命題主題原文即「以人本思維發展適應臺灣社會變遷之**普惠**科技應用」，25% 那項要求
「深度契合臺灣本土社會情境與**普惠需求**，具備長遠社會影響力」。

**既有技術資產 → 普惠論述的對應**（這是敘事重定位，不是新功能）：

| 技術事實 | 普惠論述 |
|---|---|
| 斷網仍可對話（Phase 8/9） | 偏鄉／網路不穩／無寬頻家庭一樣能用——**普惠的硬證據，不是技術炫技** |
| 音檔不出裝置、consent gate | 兒童個資保護 → 家長敢用 → 能進家庭 |
| Edge 本地推論 | 無雲端訂閱費、無 API 成本 → 低收入家庭負擔得起 |
| 教師儀表板 + 診斷 | 一位老師照顧多個孩子 → 直接對應命題的「人力結構失衡」 |

**斷網橋段應被定位為「普惠的現場證明」**，而非技術表演。
