## 拓樸決策：D-03(a) 的觸發點在哪（CONTEXT.md 列為 Claude's Discretion）

**決定：掛在 `server/app.py::api_network_mode` 的 cloud 分支，不另建裝置端輪詢器。**

依 2026-07-27 對 codebase 的查證，四項事實共同支持這個選擇：

1. **沒有第二個程序可掛。** `edge/runtime/run_edge.sh:63` 是 `exec ... -m uvicorn server.app:app`——決賽現場的 Genio 520 只跑這一個程序，學生端 UI、教師儀表板、`/api/*` 與 `pipeline` 全在其中，共用同一個 SQLite。11-PATTERNS.md「No Analog Found」欄找不到裝置端輪詢器，不是漏找，是它不存在。
2. **`api_network_mode` 是唯一的狀態轉換點。** `grep -rn "network_mode *=" server/ edge/` 顯示 `pipeline.network_mode` 只在 `server/app.py:66`（啟動預設）、`:276`、`:284` 被指派。掛在這裡就是掛在轉換瞬間本身，不需要偵測。
3. **另建輪詢器會直接違反 D-03。** D-03 明文「不得新增定時輪詢：Phase 9 已硬化離線視窗背景輪詢暫停」。一個觀察 `network_mode` 的裝置端 loop 正是那種輪詢。
4. **該處已有正確的後續鏈路。** `server/app.py:288-306` 已經是「標記同步 → `generate_diagnosis` → `add_diagnosis` → 更新 directive/profile」，正是儀表板可見結果的來源。本 plan 只需把第一步換成經閘門的版本，不必另起一套。

**同程序拓樸下「上傳」的誠實語意（必須寫進 SUMMARY，不得含糊）：**
`sync_client.push_pending()` 是裝置端對**遠端**雲端伺服器的 HTTP 發送端，`/api/sync` 是接收端。決賽是單機拓樸，兩端是同一個程序、同一個 DB——若讓 `push_pending()` 打自己的 `/api/sync`，每筆 pending 會在同一個 DB 被重新 INSERT 一次。因此 `opportunistic_sync()` 分兩條路：

- **遠端路徑**（呼叫端有給 `base_url` + `token` + `http_post`）：委派 `push_pending()`，走完整的白名單投影＋去識別化＋HTTP。這是 Phase 6 雲端 VM 部署的路徑，由 11-01 的單元測試證明其正確性。
- **本機路徑**（預設，決賽用）：沒有跨程序邊界要跨，因此不做投影、不打 HTTP，只把本批 pending 以 `store.mark_synced(seqs)` 升級為已同步。

**決賽現場真正跨出裝置的是哪一段**：是 `diagnose.generate_diagnosis()` 送往 AWS Bedrock 的診斷 prompt。該路徑的三道閘門已存在且不在本 plan 改動範圍——consent（`server/diagnose.py:660`）、`deidentify`（`server/diagnose.py:535`）、`allow_cloud` kill-switch（`server/diagnose.py:645`）。11-04 會端到端驗證這三道確實成立。
