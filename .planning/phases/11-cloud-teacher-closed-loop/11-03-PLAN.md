## 姓名資料來源決策（D-05 的 Claude's Discretion 決定）

CONTEXT.md 列了三個候選：`student_profile` payload 加 `display_name`、獨立名冊表、auth 帳號帶 name。**選定：`config.STUDENT_NAME` 常數 + `store.student_display_name()` 存取器。**

**為什麼不用 `student_profile` payload（11-PATTERNS.md 建議的最小改動選項）——這是查證後推翻的：**
`server/profile.py::build_profile()` 是**全量重算**（其 docstring 明載），只從 `prev` 帶回 `student_id` 一個鍵，其餘一律重建。而 `server/app.py:305-306` 在每次 cloud 同步時都會 `prof = profile.build_profile(...)` 然後 `store.save_profile(prof)`。因此寫進 `student_profile` payload 的 `display_name` 會在**第一次 edge→cloud 切換時被靜默清掉**——正好是決賽橋段的那一刻。這個選項是陷阱，不採用。

**選定方案的理由：**
- `server/store.py:37,67-69` 已有 `_FALLBACK_STUDENT_ID` + `config.STUDENT_ID` + `_student_id()` 的三層解析範式；姓名鏡像同一個形狀，零新概念。
- `server/config.py:31-33` 的「裝置與學生識別（決賽 demo 固定值）」區塊就是這類常數的既有歸屬地。
- 決賽為單一學生、距離決賽 3 天，這是最小且不會被其他程式碼路徑清掉的改動。
- 滿足 D-05 的硬要求：**硬編字串從 HTML 消失、儀表板從 API 讀**。常數住在 server 端、經授權端點下發，符合「姓名存在 server 端（即儀表板讀取的同一個 DB／程序）」的原文。

**多學生名冊**屬 CONCERNS.md 已登錄的 deferred 項目，不在本 phase。

## `STUDENT_QUERY` 不在本 plan 範圍

`web/teacher.html:260` 的 `var STUDENT_QUERY = 'STUDENT-AMING-004';` 是驅動「要查哪個學生」的 demo 常數，與 D-05 要求的「姓名不得是 mock」是兩件事。D-05 只要求姓名真實化。**不得**把它擴張成多學生支援（deferred）。但 `:200` 那個**顯示用**的硬編學生編號要改為從同一份 API 回應渲染，避免同一個值在頁面上被硬編兩次。
