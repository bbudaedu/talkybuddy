<objective>
把 10-01～10-04 的 spike 產物（provider 探測、shape 固定、放置量測層、Day-1 探針、ADR 決策）
接成一個**契約完整、可被既有系統選用**的 NPU ASR 引擎——`server/asr_npu.py`。

Purpose: NPU-02 要求「ASR 經 NPU delegate 加速，含 per-op 放置 logging；算子不支援時退 CPU，不得靜默
偽成功」，且必須是**真的跑推論**（有意義的逐字稿），不是 10-03 那種「餵零值假輸入只為量放置比例」的
探針。10-03/10-04 的產物只回答了「NPU 到底有沒有動」；本計畫回答「NPU 動了之後，ASR 能不能真的工作」。

**這是本 phase 風險最高的一個計畫**：sherpa-onnx 的 Python API 把 provider 白名單寫死在 C++ 編譯期
（RESEARCH.md Pitfall N1），所以繞過 sherpa-onnx 之後，fbank 前處理與 CTC 解碼都要自己重建，不是接一個
現成函式。RESEARCH.md Pitfall N2/N3 也已指出：fixed-shape 的 pad/truncate 邏輯、以及未來 10-06 的
FP32/INT8 A/B，都必須共用同一套新前端，否則「reimplementation bug」與「量化品質退化」會混在一起、
無法歸因。

Output: `server/asr_npu.py`（新引擎）、工廠/設定/status 端點三處小接線、與可離線跑的單元測試。
本計畫**不**修改 `server/asr_sensevoice.py`——CPU 基線是永久保留的 fallback，不是被取代的舊路徑。
</objective>
