<objective>
建立本 phase 唯一的「證據層」：把 ONNX Runtime 自己吐的節點放置日誌，變成可計數、可斷言、可上 HUD 的結構化資料。

Purpose: `PITFALLS.md` Pitfall 1 與 NPU-02 的核心要求是「不得靜默偽成功」。
`available() == True`、session 建得起來、推論跑得完，全部都不構成 NPU 加速的證據；
唯一的 ground truth 是 ORT 自己在 session 初始化時印出的 `VerifyEachNodeIsAssignedToAnEp` 節點清單。
本計畫把「取得並解析這份 ground truth」做成純函式，讓它能在沒有硬體的機器上被測試——
這正是防止「口說 NPU 加速」變成無法查核宣稱的關鍵。

Output: `server/npu_placement.py` 與其測試。放在 `server/` 而非 `edge/npu_spike/`，
因為 10-03 的 spike 腳本與 10-05 的正式引擎、10-06 的 `/api/status` 都要用它，
必須是單一事實來源，不能 spike 一份、正式一份（那會讓 HUD 數字與 spike 證據脫鉤）。

本計畫**不**建立任何 ONNX session、**不**修改任何既有檔案，對 Phase 8 CPU 基線零風險。
</objective>

    在 `server/npu_placement.py` 實作 `capture_fd_output`，以 `contextlib.contextmanager` 撰寫：
    1. `os.dup(fd)` 保存原 fd。
    2. 建立 `tempfile.TemporaryFile()`，`os.dup2(tmp.fileno(), fd)` 把目標 fd 導向暫存檔。
    3. `yield` 一個小型結果物件（`dataclass` 或簡單 class，欄位 `text: str`、`truncated: bool`，初始為空字串／False）。
    4. `finally` 內：先 `os.dup2(saved, fd)` 還原並 `os.close(saved)`，再把暫存檔倒回開頭讀出，套 `MAX_CAPTURE_BYTES` 上限（超過則只留前 `MAX_CAPTURE_BYTES` 位元組並設 `truncated = True`），以 `errors="replace"` 解碼填入結果物件。還原一定要排在讀取之前，避免讀檔期間的任何輸出又被吞掉。

    模組 docstring 追加說明：ONNX Runtime 的 verbose 日誌由 C++ 層直接寫 fd 2，Python 層的 `redirect_stderr` 只換掉 `sys.stderr` 物件、攔不到；這是本函式存在的唯一理由，不是為了通用日誌收集。並註明呼叫端有義務在離開後把 `ort.set_default_logger_severity` 調回原值（正式引擎在 10-05 落實）。

    GREEN 後 commit `feat(10-02): add fd-level stderr capture for ORT verbose logs`。
