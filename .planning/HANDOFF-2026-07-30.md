## ⚠️ 下次接手的第一件事（不做的話後面全白做）

**`local_client` 與 `live_client` 不能共存。** 它們搶同一顆 power 鍵
（evdev 允許多 reader，兩個都會收到按鍵）與同一支 USB 麥克風（ALSA 獨佔）。

實測後果：`arecord: audio open error: Device or resource busy` → 上行 0 bytes
→ 玩偶完全沒反應。**2026-07-30 有連續三輪測試因此無效**，而當時誤判成
「近場門檻擋掉聲音」「孤兒 arecord」，查了很久才發現是另一個 service。

而且 `talkybuddy-local-client.service` 是 `enabled` 的，**開機必定自動起來**。

修法（擇一）：

1. `systemd` 的 `Conflicts=`：兩個 unit 互斥，起一個自動停另一個
2. 合併成單一程式，用環境變數（如 `TALKYBUDDY_EDGE_MODE=turn|live`）切模式

**在做任何 S2S 實測之前先做這件事**，否則測試結果不可信。
臨時解法：手動 `systemctl stop talkybuddy-local-client` 再跑 `live_client`。

## 今天推翻的三個既有認知（別再照舊資料走）

### 1. 板上「自訂鍵」不能用，觸發鍵是 **power 鍵短按**

`KEY_HOME`(102) 在 kernel 位元圖有註冊，但**那顆實體鍵不送任何 evdev 事件**
（按數十次、跨重開機、繞過 Python 直接 `dd` 讀都是 0 bytes；以耳機孔插拔事件
作對照組證明觀測方法有效）。**註冊 ≠ 接得上。** 2026-07-29 的記錄是錯的。

前提：`systemd-logind` 必須 `HandlePowerKey=ignore`，否則按下去是關機。
`provision_device.sh` 步驟 [3/3] 會寫入持久的 drop-in。

⚠️ demo-only：PMIC 長按強制斷電是硬體行為、軟體攔不住（約 8–10 秒）。

### 2. **ALSA mixer 對 3.5mm 輸出完全無效**，音量只能靠軟體

實測：`Lineout` 7→3（-4dB）聽不出差別；`ADDA_DL_GAIN` 97%→13%（約 -18dB）
**音量完全沒變**。3.5mm 後方應該接了硬體固定增益的功放
（`Ext_Speaker_Amp` 寫入報 `Invalid argument`）。

先前以為 `Lineout` 在控制音量，其實它從 0% 調到 39% 只是把類比末級
**從靜音打開**，不是在調音量。

→ 用 `audio_io.scale_pcm16()` 直接改 PCM 樣本值，這是唯一有效的方式。
   `TALKYBUDDY_EDGE_PLAYBACK_VOLUME=0.15` 實測有效。

### 3. `/ws/live` 必須帶 **`?mode=continuous`**

server 以這個 query 參數分流。少了它 server 走回合式、等 `{"type":"user_end"}`，
而持續串流的 client 從不送 user_end → 兩邊互等 → 上行 25.8s、下行 0 bytes。

（`app.py` 的 docstring 與 `_uplink()` 的註解看似矛盾，其實是描述兩種模式，
讀片段就下結論會誤判——我踩過。）

## S2S 現況：能跑，但體驗還沒到可 demo

**已證實可用**：`live_s2s: true`，`scripts/verify_ws_live_e2e.py` 拿到 10 段
transcript + 28 秒語音，Nova Sonic 用繁中做英語伴讀、會放慢語速帶讀。

**裝置端 `live_client.py` 的實測問題**：

| 問題 | 現況 |
|---|---|
| 自我迴音 → 自己打斷、自己一直說 | `PlaybackGate` 緩解（依音訊長度推算播放時長）|
| 但閘門讓體驗**降級成回合式** | 使用者原話：「感覺回到回合、感覺降級」|
| 環境噪音誤觸 | 旁邊電視講的「我明白了」被判成插話（使用者確認不是他說的）|
| `underrun` 斷斷續續 | `--buffer-time=2s` 後 16 次 → 2 次，但剩下的是**模型生成 4–6 秒空檔**，緩衝救不了 |

**根本限制**：喇叭與麥克風同在玩偶內、裝置**無 gcc/cmake 裝不了 AEC**，
真正的全雙工在這個硬體上做不到。half-duplex 閘門是在「自我打斷」與
「吃掉孩子的話」之間找平衡，兩邊都不完美。

**現場可調參數**（都在 `live_client.py`，env var）：

```
TALKYBUDDY_EDGE_PLAYBACK_TAIL_S     2.0 較穩 / 0.2 較接近全雙工
TALKYBUDDY_EDGE_PLAYBACK_VOLUME     0.15（喇叭小聲也直接減少迴音）
TALKYBUDDY_EDGE_NEAR_FIELD_PEAK     0.06；設 0 停用（麥克風拉遠時會誤擋使用者）
TALKYBUDDY_EDGE_PLAYBACK_BUFFER_US  2000000
```

## 除錯方法論（今天學到的，會省下很多時間）

1. **先排除觀測管道，再懷疑硬體。** 經 SSH 前景執行的診斷工具，連線一斷輸出就
   卡在死掉的 TCP 裡，看起來與「按了沒反應」一模一樣。用
   `nohup ... --seconds N > /tmp/x.log` 讓結果留在裝置本機。
2. **要有對照組。** 「按鍵收不到事件」是靠耳機孔插拔事件（`event0`）證明觀測
   方法有效，才敢對 0 bytes 下結論。
3. **`pkill -f` 會殺掉自己所在的 shell**（cmdline 含該字串）。今天犯了四次。
   用 `pgrep -x <名稱>` 比對行程名，或把停止與啟動拆成兩條指令。
4. **不要把診斷資訊丟進 `DEVNULL`。** `arecord`/`aplay` 的 stderr 一度被我吞掉，
   結果只看得到「session 立刻結束」，完全無法定位。
5. **凡是阻塞呼叫都不能直接放進 async 迴圈。** 同一類錯誤今天犯了三次
   （`wait_for_trigger`、`sink.write`、`preflight` 讀錯 env 來源）。
