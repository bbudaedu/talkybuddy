# 落地維運模型

> 建立於 2026-07-27。用途：決賽評分「可行性（20%）」明文要求「實際落地維運的**模擬與評估**」。
>
> **資料紀律**：本檔區分三種陳述——
> `實測` = Phase 7/8/9 在 Genio 520 真機上量到的數字，附出處；
> `推導` = 由實測值計算而得，計算式寫明；
> `待決` = 需要團隊或校方拍板，**不是**工程可獨力決定，明確標示不填假數字。

> 不要說「一台學校只要 X 元」——那個數字我們沒有。

### 1.3 已驗證的硬體限制（影響部署方式）`實測`

| 項目 | 狀態 | 對部署的意義 |
|---|---|---|
| 3.5mm 音訊 | ✅ 已驗證可用 | 麥克風／喇叭走類比，不依賴 USB 音效卡 |
| 乙太網路 | ✅ 可用 | **有線是唯一可靠的網路路徑** |
| 藍牙 | ⚠️ **本機現況不可用**（非硬體缺失，見下） | 目前無法用藍牙喇叭／耳機 |
| USB WiFi | ❌ 不可用（kernel 未編驅動、板上無編譯環境） | 這條路不通，別再試 |
| 內建 WiFi | ⚠️ **規格書有，本機未啟用** | 若能啟用則不需網路孔 |

> ⚠️ **2026-07-29 更正措辭。** 先前寫「藍牙與 USB WiFi 皆不可用是這塊板子的實測結果」，
> 前半句的**歸因**站不住：
>
> - 實測到的事實是 SDIO/PCIe 匯流排探測不到晶片、沒有 `hci0`——**這是現況為真**
> - 但 **G520 SoM 規格書載明 Wireless Connectivity 為 WiFi-5（802.11 a/b/g/n/ac）
>   + Bluetooth 5.3**，且供應商表示**同型板子跑 Android 可用**
> - DTB 裡根本沒有 wifi/bt 節點時，「匯流排探測不到」是**弱證據**，
>   不能反推晶片不存在
>
> **所以正確的說法是「本機這套 Yocto 映像沒有啟用無線」，不是「這塊板子沒有無線」。**
> 對評審講錯方向會被規格書打臉。
>
> **部署結論不變**：現況必須用**乙太網路**（已驗證 1Gbps）或**完全離線**；
> 手機 USB 網路共享為已驗證的備援（`rndis_host`/`cdc_ether`/`cdc_ncm` 皆在 kernel 內）。
> 改變的只是「為什麼」——是軟體堆疊缺口，**可修**，不是硬體死路。
>
> 諷刺的是，這反而強化了離線論述——**在沒有網路孔的教室裡，這台裝置只能離線跑，
> 而它本來就設計成離線可跑。**

| **合計** | | **≈ 1.4 GB** |

> 開發目錄的 `models/` 是 5.3 GB，因為含 NPU 實驗留下的 FP32／folded／pinned
> 等多份 SenseVoice 變體。**部署只需上表這 1.4 GB。**

### 2.2 執行期資源 `實測`（Phase 8，`edge/EDGE_TURN_LOOP_VALIDATION.md` §B）

| 指標 | 實測值 |
|---|---|
| 峰值 RSS（uvicorn 673 MB + llama-server 2,115 MB） | **≈ 2,723 MB** |
| 裝置總記憶體 | 4,096 MB（實際可用 3,794 MB） |
| headroom | 33.5% |
| CPU | 6× Cortex-A55 + 2× Cortex-A78，llama-server `--threads 6` |
| LLM context | 512 tokens（edge profile 預設） |

> **記憶體是這台裝置最硬的約束。** 2,723/4,096 已用掉三分之二；
> 這也是 NPU 軌道最終卡死的原因（937 MB 的 float TFLite 連編譯都 OOM，
> 見 `edge/npu_spike/ADR-npu-path.md` §9）。
> 維運上的意義：**同一台裝置不要再疊加其他常駐服務。**

## 3. 使用者體驗基準 `實測`（Phase 8 真機）

> ⚠️ **2026-07-29 更正：下表的 2.96–2.99 s 在真實對話中重現不出來。**
> 那三筆是**同一句話重複講**量到的（KV cache 命中 292/293），真實對話每句都不同、
> 共同前綴只有 8 個字，每輪要多重算 57 token ≈ 1.67 s。
> **現場應期待 4–5 s**（2026-07-29 實測 `round_total` 4.8–6.3 s）。
> 完整證據鏈與對帳見 `edge/LATENCY_2.96S_EXPLAINED.md`。**簡報不得引用 2.96 s。**

| 情境 | 實測延遲 | 判定 |
|---|---|---|
| ~~穩態回合（暖機後連續對話）~~ ⚠️ 複測同一句 | ~~2.96–2.99 s~~ | 條件不成立，見上方 |
| **穩態回合（換句話講，真實對話）** | **4.0–5.1 s** `2026-07-29 實測，threads=6` | ❌ 未達 3–4 s 門檻 |
| ↑ 同上，修 threads 之前 | 4.8–6.3 s | — |
| 冷啟動首句（開機暖機後第一句） | **5.85 s** | ❌ NO-GO（門檻 3–4 s） |
| 冷啟動首句（完全未暖機） | 10.03 s | ❌ |
| ASR 單段 | 405 ms | — |

**已知缺口與現場對策**：真實對話的穩態回合就已超出 3–4 s 門檻。兩個已定位的原因：

1. **`--threads` 從 6 退回佔位的 4**（prefill 慢 1.47×）。ELOOP-03 早就掃描出 6 最佳，
   但只用 env override 套在裝置上、預設值沒改回來。**已改為 6、已上裝置、已實測**
   （2026-07-29）：`llm` 平均 4,696 → 3,643 ms（**快 22%**），但 `round_total`
   仍是 **4.0–5.1 s**。**只佔約 1 秒，不足以達標。**
2. **固定回覆格式指令放在 user message 尾巴而非 system prompt**，每輪重算。
   修法已試過並**放棄**：`edge/PROMPT_ORDERING_FINDING.md` 實測它省 1.2 s，
   但中文稱讚合規率 5/5 → 0/5，產品行為壞掉。這條路不要再走。

現場對策：**主持人先講一句暖場**，避開 10 s 的完全未暖機首句。
但暖場**不能**把回合壓進 3 s——那個數字建立在複測同一句上。
誠實的講法是「約 4–5 秒完成一輪，**斷網時完全不變**」；重點是不中斷，不是快。

## 4. 部署到一間學校：時程與步驟 `推導`

以下步驟全部來自 `docs/DEPLOY_EDGE.md` 的實際流程（Phase 7 已在真機跑通），
時間為依既有流程推導，**未做過真實校園部署，非實測**。

### 4.1 一次性前置（每個新板卡，約 2–4 小時）

| # | 動作 | 說明 | 估時 |
|---|---|---|---|
| 1 | 燒錄 Yocto image | `Rity Demo Layer 25.1.1-release (scarthgap)` | 40 min |
| 2 | 核對 `/proc/cpuinfo` Features | **決定 llama.cpp `-march` 旗標，不可沿用假設** | 5 min |
| 3 | 開發機交叉編譯 llama.cpp | `edge/deploy/build.sh`（需 aarch64 工具鏈） | 20–40 min |
| 4 | `push.sh` 推送程式碼 + binary + 1.4 GB 模型 | 區網 rsync；**大檔傳輸期間連線會斷，需重試迴圈** | 20–60 min |
| 5 | `provision_device.sh` 裝 Python 相依 | 全數有 aarch64 預編譯 wheel，免編譯 | 15 min |
| 6 | `run.sh` 啟動 + health check | | 5 min |
| 7 | 音訊迴路實測（3.5mm 麥克風／喇叭） | | 30 min |

> **步驟 4 是實際的痛點。** Phase 8 與本次 NPU 傳輸都遇到「大檔傳輸期間 Genio 連線中斷」，
> 需要 `rsync --partial --append-verify` + 重試迴圈才能完成。校園現場網路更不可控，
> **應改為離線預載**（見 §4.3）。

### 4.2 每次軟體更新（約 10 分鐘）

`push.sh` → `run.sh`。模型不變則不重傳，只推 `server/` 與 `edge/runtime`。

### 4.3 校園部署應該怎麼做（`待決`，建議案）

上面那套是**開發者的部署迴圈**，不適合校園。建議改為：

- **出貨前預載**：模型與程式在團隊端完整燒進 image，到校即插即用，**不在校園做 rsync**。
- **到校動作縮到三步**：接電源 → 接音訊 → 開機自檢（LED／語音提示「我準備好了」）。
- 目標：**校方人員零技術操作**，到校佈署 15 分鐘內完成。

此路徑**尚未實作**（目前沒有 image 打包流程），列為落地前必要工程。

## 5. 誰來維護、維護什麼

### 5.1 維運動作分級

| 層級 | 動作 | 執行者 | 頻率 |
|---|---|---|---|
| L0 | 開關機、接線、音量 | **導師或學生本人** | 每日 |
| L1 | 重開機排除卡頓、確認自檢通過 | 校內資訊組 | 需要時 |
| L2 | 軟體更新、模型更新 | 團隊遠端或到校 | 每學期 |
| L3 | 硬體故障換機 | 團隊／供應商 | 故障時 |

**設計上的關鍵**：離線運作意味著 **L0/L1 不需要網路、不需要團隊介入**。
這是與「靠網路的數位學伴」最大的維運差異——後者一斷線就整堂課停擺，沒有 L0 可做的事。

### 5.2 已知的維運風險（`實測`，不得隱瞞）

| 風險 | 現況 | 落地前必須處理 |
|---|---|---|
| **sshd 無驗證**（`root` 免密碼免 key） | **2026-07-29 複驗仍成立**：`passwd -S root` → `NP`（無密碼）、`/root/.ssh/authorized_keys` **不存在** | ⛔ **必須修**。同網段任何人可免憑證取得 root。校園網路非受控。見 `edge/BOARD_BRINGUP_DECISION.md` §4 |
| uvicorn 綁 `0.0.0.0:8787` | 已接受風險（Phase 7） | 校園部署應限制網段或改綁 loopback + 本機 UI |
| ~~大檔傳輸連線中斷~~ **上游網路不穩** | **2026-07-29 歸因更正**：不是裝置或傳輸問題，是網路來源（手機分享）本身會斷；恢復後 `uptime` 連續可證裝置從未重開 | 以 §4.3 的預載方案迴避；現場改接乙太網路可大幅降低 |
| 冷啟動 5.85 s | 根因已知，**修法已試過並放棄**：`edge/PROMPT_ORDERING_FINDING.md` 實測它省 1.2 s 但中文稱讚合規率 5/5 → 0/5 | 非阻擋，但影響第一印象。**這條路不要再走** |
| 換板卡需重核 `-march` | 已文件化 | 流程風險，非缺陷 |

## 6. 營運成本結構：這是最強的可行性論據

### 6.1 邊際成本 `推導`

| 模式 | 每回合對話的邊際成本 |
|---|---|
| **Edge（本方案主線）** | **雲端 API 成本 = 0**。只有電費 |
| Cloud（對照） | 每回合 ASR + LLM + TTS 的 API 呼叫費，隨使用量線性增加 |

**結構性差異**：edge 模式下，一台裝置服務一個孩子一整年，**雲端帳單是零**。
使用越多越划算；雲端方案則相反。

> ⚠️ `待補`：**我們沒有實測過雲端模式的 per-turn 成本。**
> 要把這段講成數字（「一個孩子一年省 X 元」），需要跑一次計費量測
> （固定 N 回合、記錄 token 數與 TTS 字元數、對照公開價目）。
> 在拿到那個數字之前，**只講結構（零邊際成本 vs 線性成本），不講金額。**

### 6.2 對照政府現行方案

依 `docs/NEEDS_EVIDENCE.md` §C1，教育部數位學伴計畫的成本結構是
**大學生鐘點 + 排班行政 + 網路頻寬**，一年覆蓋 1,600 餘位學童。
其成本**隨服務人數線性增加**，且受限於大學生的可排班時數。

本方案的成本結構是**一次性硬體**，服務時數不受人力限制。

> 這是可行性 20% 那項最該講的一句話：
> **「他們的瓶頸是人和網路，我們的瓶頸是一次性硬體採購。」**

### 6.3 若評審問「同時 30 個孩子用會怎樣」

**先分清楚問的是哪一種部署**，兩者答案完全不同：

| 部署 | 併發情形 | 誠實答案 |
|---|---|---|
| **Edge（玩偶）** | **一童一機**，每台裝置只有一條連線 | 併發不存在。這正是「零邊際成本」的來源 |
| **Cloud（伺服器）** | ASR／TTS 是 in-process 單例，所有學生連線共用 | **不會崩，但會排隊** |

雲端那格的細節（2026-07-29 查證）：

- ASR 與 TTS 的 native 呼叫**已由 `threading.Lock` 序列化**
  （`asr_sensevoice.py:105`、`asr_whisper.py:63`、`tts.py:227`，PR #7 `658383d` 引入）。
- **這修掉的是 segfault，不是擴展性。** 序列化的意思是第 30 個孩子要等前 29 個做完，
  延遲隨併發數線性成長。
- **從未做過壓力測試。** 上面是讀程式碼得到的結論，不是實測。

> 所以可以誠實說的是：「雲端版同時多人不會崩，但目前是排隊處理，**我們沒有壓測過**。
> 要支撐一個班級需要把 ASR／TTS 拆成獨立的 worker——那是 v2 的工程，不是今天的宣稱。」
>
> 這一格先前記載的答案是「會 segfault」，PR #7 合併後已不成立。

## 8. 尚缺與限制（不得粉飾）

- **未做過真實校園部署。** §4 的時程是依既有開發部署流程推導，不是實測。
- **無量產 BOM 報價。** §1.2 只有 EVK 公開價，不等於部署成本。
- **雲端 per-turn 成本未量測**（§6.1），因此「省多少錢」目前講不出數字。
- **§4.3 的 image 預載流程尚未實作**，目前只有開發者用的 rsync 部署迴圈。
- **sshd 無驗證是明確的安全缺口**，落地前必修。
- **冷啟動 5.85 s 未達門檻**，現場靠主持人暖場規避，不是修好了。
- **遠端連線多次中斷**（ping 100% 掉包）。原推測為 Tailscale subnet route 中斷，
  **2026-07-29 使用者澄清了真正原因：網路來源是他的手機網路分享給路由器**，
  不穩或被拔線就整條斷——**不是裝置故障，也不要據此推論 Yocto 或硬體有問題**。
  恢復後 `uptime` 連續即可證明裝置從未重開。
  **決賽現場若依賴遠端連線，這仍是單點故障；現場應規劃為完全離線操作**，
  但理由是現場網路環境不可控。
