# 設計：無螢幕裝置的遊戲開局（語音指令 + 主動邀請）

日期：2026-07-29　狀態：已核准，待實作

## 問題

`.planning/HANDOFF-2026-07-29.md` ROI 第 3 項寫的是「遊戲前端 UI —— 現在老師得用
curl 開局，現場不現實」。**但那個前提是錯的：邊緣終端開發板設計上沒有螢幕。**
按鈕要畫在哪裡的問題不存在，開局只能靠聲音。

三個遊戲（`server/games.py`）功能完整、`/api/game` 也完整，缺的是**觸發方式**。

## 掛載點（已查證）

裝置端 `edge/runtime/local_client.py` 走的是**既有的 `/ws/talk` 協定**，不是第二套
wire protocol。因此瀏覽器與無螢幕原生迴路吃到的是同一個
`server/pipeline.py::_process_text()`——**改一處，兩邊都生效**。

意圖偵測插在 `pipeline.py:384`「遊戲進行中 → `games.judge`」判定**之前**。

## A. 語音指令開局

新模組 `server/game_intent.py`，純函式、無狀態：

| 函式 | 回傳 |
|---|---|
| `detect_start(text)` | game kind 或 `None` |
| `detect_stop(text)` | `bool` |
| `detect_yes_no(text)` | `True` / `False` / `None` |

遊戲名一律從 `games.GAMES` 的 `zh`/`en` 欄位讀取。**不在此處硬編第二份清單**——
`games.py:600` 的註解已經警告過：兩份清單遲早不同步，而不同步的症狀是「開局沒反應」，
現場最難查的那種。

**防誤觸：意圖詞與遊戲名必須同時命中**（`玩|來|開始|我要|想` ＋ 遊戲名）。
單講「點餐」不開局——餐廳本來就可能是對話主題。

開局後的回覆取自 `games.prompt(state)`，走 TTS，`llm=0ms`。

## B. 主動邀請

`pipeline` 新增 `_pending_invite: str | None`。

- **觸發**：`_stuck_streak >= STUCK_STREAK_THRESHOLD`（連續 2 輪沒命中詞庫，欄位已存在）
  ＋ 沒有進行中的局 ＋ 沒有待回覆的邀請 → 該輪回覆尾巴接邀請句
- **下一輪**：答應 → 開局；拒絕 → 清掉；**沒回應也清掉**

> 「沒回應就不糾纏」是刻意的：孩子已經卡關，再追問是二次挫折。

主動邀請固定推 **火眼金睛**（`i_spy`）：它門檻最低（看到什麼說什麼），是卡關情境下
唯一合理的選擇。另外兩個遊戲靠 A 用講的叫出來。

## 刻意不做

- **不讓 LLM 判斷意圖、不改 `user_prompt`**。`PROMPT_ORDERING_FINDING.md` 記載動
  `user_prompt` 讓中文稱讚合規率從 5/5 掉到 0/5；且 edge LLM 一輪 4–5 秒。
  開局是最需要確定性的動作，不能放在最不確定的路徑上。
- 不做診斷資料驅動的遊戲選擇（v2）。

兩段都是純規則，**斷網與連網行為一模一樣**——這本身就是要展示的東西。

## 測試策略（紅線）

2026-07-29 的教訓：89 條遊戲測試全過，但遊戲根本不會觸發，因為**沒有一條測
「開局 → 在 `/ws/talk` 講話」這條唯一的真實路徑**。

- 整合測試一律走 `/ws/talk`，比照 `tests/test_games_ws_talk.py`
- 單元測試覆蓋意圖比對的誤觸邊界（單講遊戲名不得開局）
- B 的狀態機：邀請 → 答應 → 開局；邀請 → 拒絕 → 不糾纏；邀請 → 無關回應 → 清掉
