三、缺口在哪

你想要的現況為什麼不夠
記得喜好 部分 interests 靠 scaffold.VOCAB 類別命中統計，只能得到 animal / food / school。孩子說「我喜歡恐龍」而詞庫沒有 dinosaur → 完全記不住
記得個性 無 emotional_recent 只是最近一次診斷的情緒欄位，不是跨場累積的性格側寫
主動吸引興趣 無 系統只被動回應。不會開口說「上次你說喜歡恐龍，今天我們學 dinosaur」
LLM 萃取 metadata 部分 companion_directive 是「本輪策略」不是「長期記憶」，只看最近一次診斷，沒有跨週累積

四、Memory 的四種內建策略 — 你只配了兩個

AgentCore Memory 的模型正是你描述的：events 存完整對話，strategies 用 LLM 萃取 metadata（extraction → consolidation）。四種內建策略中，你缺的兩個正好對應你要的兩件事。

策略萃取什麼你的狀態對應你的需求
SUMMARIZATION 每場練了什麼、表現如何 已配 —
SEMANTIC 關於學生的事實：興趣、已掌握詞彙、常犯錯誤 已配 「喜好」的事實層
USER_PREFERENCE 偏好、選擇、風格，建立持久使用者檔案 缺 「喜好、個性」
EPISODIC 結構化情節（情境／意圖／行動／結果），並跨情節反思，讓 agent 把過去成功的模式用到新互動 缺 「主動吸引興趣」

EPISODIC 值得特別看：它學的不是「孩子喜歡什麼」，而是 「什麼方式對這個孩子有效」——用遊戲切入有反應、直接糾錯會沉默。 那正是「主動吸引學習興趣」在系統層面的意思。

五、目標架構：雙寫，不是取代

為什麼這個設計對你的決賽敘事特別有利

離線時讀的是上次同步下來的側寫快取，所以 斷網後 AI 仍然記得這個孩子，只是不再更新。 這正好是你的核心敘事——「斷網仍可用，接上雲端更聰明」—— 而「記得孩子」會是那個敘事最有說服力的例子。

六、三個方案的取捨

AgentCore Memory ＋ 兩個新策略 建議

  • 資源已 ACTIVE，帳號已驗證，agentcore.py 已處理 actor_id 隔離（:219 明寫「Memory 會跨學生混用」）
  • 新增策略是 control plane 的設定，不改對話路徑程式碼
  • 符合「整套代理都用 AWS」——三個 Harness 已經在跑
  • 代價：斷網歸零，本地那套邏輯得留著，兩套邏輯的維護成本不會消失

openwiki 用途錯配

  • 它的記憶單位是文件，不是每輪對話；沒有 per-turn 萃取與注入迴圈
  • 是 CLI 批次工具，跑不進 1.5 秒的即時路徑，也跑不上 Genio 520
  • 但它有另一個真實用途：替這個 repo 自動生成技術文件（含 Mermaid 圖），支援 AWS Bedrock 當 provider。決賽評審要看架構時，這比人工維護的文件新

自建 LLM wiki（存 SQLite） 次選

  • 完全離線可控、零新依賴，複用現有 agent_outputs 表（store.py:171 註解明說就是為此設計）
  • 但你已經付錢開了 Memory，自建等於重造 AWS 已經做好的萃取與整併
  • 只在「決定不上 AWS」時才是首選

七、時程建議

決賽前（剩 2 天）：不要接進對話路徑

理由是具體的：注入點是 user_prompt，而 edge/PROMPT_ORDERING_FINDING.md 已用實測證明動這個位置會破壞核心產品行為—— 那次中文稱讚合規率從 5/5 掉到 0/5，還是在快取面「改善了」的情況下發生的。 今天合併 PR #7 時跑了 5 組 × 2 輪合規率驗收才敢放行；再動一次等於把已驗證的東西重新推翻。

時機做什麼風險
決賽前
（可選）		 加上 USER_PREFERENCE 與 EPISODIC 兩個策略，並開始非同步寫入 events——只寫不讀，對話路徑一行不改 零。不讀就不影響回覆
決賽現場 用現有的 interests ＋ SRS 到期詞講故事。「這孩子上禮拜 banana 沒說對，今天菜單第一個就是 banana」現在就成立（docs/GAMES.md:50） 零，已驗證
決賽後 接上 retrieve → 側寫快取 → directive_block，並跑合規率驗收 中，需重跑驗收

那個「可選」值得做。到決賽當天你就有真實累積的 events， 評審問「這套怎麼長期記住孩子」時，你能打開 AWS console 給他看真的資料， 而不是講一個計畫。而且因為只寫不讀，它不可能弄壞任何已驗證的東西。
