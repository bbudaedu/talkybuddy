# 2.96s 為什麼在現場重現不出來（2026-07-29 查證，未動裝置）

## 一句話

**2.96–2.99s 是「同一句話重複講」量出來的最佳值**，真實對話拿不到那個 KV cache 命中率。
簡報引用它會與現場實況不符。**現場一律講 4–5 秒。**

> ### ✅ 2026-07-29 真機驗證：threads=6 已套用並量測
>
> **`llm` 平均快 1,053ms（22%），但 `round_total` 仍是 4.0–5.1s。**
> 本文件原先預測「修掉 threads 後可望回到 3.5–4 秒」——**那個預測太樂觀，已更正**。
>
> 同一支 `probe_latency.py`、同樣 4 個輸入（蘋果／香蕉／麵包／牛奶）、同一條連線：
>
> | `llm` (ms) | 1 | 2 | 3 | 4 | 平均 |
> |---|---|---|---|---|---|
> | `threads=4`（合併後，本日稍早） | 4,442 | 4,396 | 4,891 | 5,056 | **4,696** |
> | **`threads=6`（本次）** | 3,726 | 3,636 | 3,976 | 3,232 | **3,643** |
>
> `round_total` 本次量到 **4,014–5,146ms**（前次 4.8–6.3s）。
>
> **結論：threads 是真的原因之一，但只佔約 1 秒。**剩下的落差來自每輪重算 57 token
> 的 prompt，而那條路（移進 system prompt）已經試過並因為破壞產品行為而放棄。
> **4–5 秒就是這套硬體＋這個 prompt 結構的實際數字。**

## 證據鏈（全部來自本 repo 既有紀錄，非新實測）

### 1. 那三筆 2.96s 的 cache 命中率是 292/293

`EDGE_TURN_LOOP_VALIDATION.md:37`：

> **根因**：llama-server 對同一 slot 的 prompt 前綴做 KV cache 重用（`cached_tokens` 命中 292/293）

293 個 prompt token 只重算 1 個——**只有整段 user message 一字不差時才可能**。

### 2. 但真實對話的共同前綴只有 8 個字

`PROMPT_ORDERING_FINDING.md`：user message 的第一行是每輪必變的
`學生剛剛說：「{student_text}」`，所以

> 兩個連續回合的共同前綴只有 **8 個字**。

同一份文件實測穩態要重算 **57–58 token、1,669–1,679 ms**。

**兩份文件對同一件事給出相斥的數字，因為量的不是同一件事**：一個是複測同一句，
一個是換句話講。

### 3. Phase 8 自己的紀錄裡本來就有 5.85s 那一筆

`PROMPT_ORDERING_FINDING.md:5` 引用的 Phase 8 單回合分解：

```
{'asr': 405, 'llm': 4170, 'tts_first': 1209, 'round_total': 5852}
```

**這筆才是換句話講的真實回合**，而它和 2026-07-29 實測的 4.8–6.3s 完全同一區間。

### 4. threads 從 6 悄悄退回 4

`EDGE_TURN_LOOP_VALIDATION.md:27` 的 llama-bench 掃描選定 6，但只用
`TALKYBUDDY_LLM_THREADS=6` env override 套在裝置上，`server/config.py` 的預設仍是
佔位的 4，而 `run_edge.sh` **沒有設定這個變數**。2026-07-29 實測裝置正是 `--threads 4`。

| threads | pp128 | tg128 |
|---|---|---|
| 4 | 26.49 | 10.50 |
| **6** | **39.06** | **12.35** |

prefill 慢 **1.47×**。已於 `c<pending>` 把預設改為 6，並加測試釘住
（`tests/test_llm_threads_default.py`）。

## 對決賽的意義

1. **簡報不要引用 2.96s。** 誠實可用的講法：「edge 端在裝置上約 4–5 秒完成一輪，
   斷網時完全不變」——重點本來就是**不中斷**，不是快。
2. **threads=6 已於 2026-07-29 套上裝置並實測**：`llm` 快 22%，但 `round_total`
   仍是 4.0–5.1s（見上方表格）。**現場數字不變，仍講 4–5 秒。**
3. **真正的結構性修法（把固定規則移進 system prompt）已經試過並放棄**——
   `PROMPT_ORDERING_FINDING.md` 實測它讓中文稱讚合規率 5/5 → 0/5。省 1.2 秒但產品行為
   壞掉，不划算。這條路不要再走。

## 方法論教訓

**複測同一句話會給出假的信心**——和 `NATIVE_KWS_PLAN.md` 那個「用自家 TTS 合成音驗
KWS 通過了、真人卻失敗」是同一類錯：量測條件比真實情境仁慈。

穩定性複測要換不同的輸入，否則量到的是 cache 不是系統。
